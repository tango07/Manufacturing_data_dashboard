# CLAUDE.md: Axiom Auto Components Manufacturing Intelligence

Loaded at the start of every session. Keep it short and current. Detailed rules live in `skills/` and specialised workers in `agents/`. Move both into `.claude/` at the repo root to activate them automatically.

## Project purpose

Build a reproducible pipeline, database and management dashboard for Axiom Auto Components (3 plants, 4 lines per plant). The dashboard answers the five leadership questions and recommends three ranked actions. The brief is in `dashboard-build-prompt.md`; the current status is in `README.md`.

## Commands

- Install: `pip install pandas openpyxl pytest`
- Full data: `python -m pipeline.run --input data/raw/full_export`
- Recompute from the database: `python -m pipeline.run --from-db`
- Tests: `python -m pytest tests -q`
- Dashboard: open `dashboard/index.html`, generated by the pipeline from `dashboard/template.html`

## Architecture

- Data flows through `data/db/axiom.db` (SQLite). Raw tables are `raw_*`, clean ones `clean_*`, rejected rows `quarantine_*`. Also `dq_exceptions`, `run_fact`, `kpi_snapshot` and `ingest_log`.
- `pipeline/` is deterministic Python: ingest (`ingest.py`, `load.py`), database (`db.py`), DQ rules (`dq.py`), joins and reconciliation (`transform.py`), KPIs (`kpis.py`), leadership (`leadership.py`), orchestration (`run.py`). Config and thresholds are in `config.py`.
- `api/assistant_core.py` holds LLM logic (key handling, prompt, guardrails, grounding), without a server.
- `dashboard/template.html` and `dashboard/aggregate.js` build the page. The aggregation code sums the exported cleaned rows for the chosen dates, plant and shift.
- `docs/` holds `ASSUMPTIONS.md`, `ACTION_PLAN.md` and `GENAI_EVIDENCE.md`.

## Non-negotiable rules

1. Never hardcode, print, log or commit an API key. Keys come from `LLM_API_KEY` on the server only.
2. Every KPI definition lives in the pipeline. The dashboard adds up the cleaned rows the pipeline exports (`rows` in kpis.json, via `dashboard/aggregate.js`) for the dates chosen, using sums and ratios of sums only. `tests/pipeline/test_aggregate.py` checks those totals against the pipeline for the same windows. The LLM only narrates values it is given.
3. Aggregate child tables to Run_ID before joining to production runs.
4. Rates are sums of numerators over sums of denominators. Never average row-level rates.
5. Never silently drop data. Bad rows go to quarantine with a rule ID, a reason and a source row.
6. Every ratio shows its denominator, coverage and record count. Zero denominators return "n/a" with a reason.
7. Never add minutes to units, or any other unlike quantities. Use USD for cross-segment comparison.
8. Write tests before implementation for every DQ rule, join and KPI.
9. When data does not support an answer, say "Insufficient evidence" and name the data needed.
10. Record assumptions in `docs/ASSUMPTIONS.md`. Ask the user only when a choice would change the business conclusion.

## Environment note

SQLite cannot write to the Desktop mount in the build sandbox ("disk I/O error"). Run the pipeline on a local copy, then copy the database file across. Do not open the Desktop database file with SQLite from the sandbox: opening it truncated the file once. Leftover `-journal` files can roll the database back, so delete them before shipping.

## Known data facts (full export)

- Four flat workbooks, one table each, 1,000 rows per file, header in row 1. The stacked sample is still supported.
- Known defects in the export: 8 production rows with blank Run_ID; 8 invalid dates per table ("INVALID_DATE"); RUN-000302 duplicated; 8 negative downtime minutes; 8 moisture values of 105; 8 good-units-above-produced rows; 8 defect counts above sample size; codes MC-99 and SUP-99 not in production; trailing spaces and lower-case codes; "Fail" and "Pass" casing.
- Unit_Cost_USD is assumed per unit (A-01). Confirm with Finance.
- SUP-04 accounts for all incoming QC failures in the export.
